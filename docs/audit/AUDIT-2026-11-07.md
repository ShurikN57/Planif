Base auditée : `720d613` (version publique `2026.10.22.01`), branche `main`.
Périmètre : code applicatif, tests, CI/CD, sécurité, données, documentation et processus de travail.
Hors périmètre : le backend Firebase `strava-mobile-2f93f` (pas dans ce dépôt) et la validité scientifique détaillée de chaque règle d'entraînement.

## 1. Synthèse

Planif est une PWA statique (GitHub Pages, sans build ni dépendance) qui génère des plans d'entraînement course à pied, calcule les allures et la charge, et s'interface avec COROS (OAuth PKCE) et un service Strava via Firebase Auth.

**Avis général : le fond est solide, la forme freine la suite.**

| Domaine | Note | Commentaire court |
| --- | --- | --- |
| Fonctionnel / métier | 🟢 Très bon | Moteur riche, règles explicites, distinction claire « science / heuristique Planif ». |
| Tests de non-régression | 🟢 Bon | 21 fichiers, tous verts en ~4 s ; empreintes de 252 plans ; scripts d'audit reproductibles. |
| Sécurité | 🟢 Bon | CSP stricte avec hash, SRI sur Firebase, PKCE, jetons en `sessionStorage`. Quelques points à durcir. |
| Lisibilité / maintenabilité | 🔴 Faible | Code écrit « minifié » (lignes jusqu'à 3 977 caractères), `planif-ui.js` = 190 Ko, ~98 variables globales mutables. |
| Robustesse des dates | 🟠 Moyen | Les tests échouent hors du fuseau `Europe/Paris`. |
| Données utilisateur | 🟠 Moyen | Tout est en `localStorage`, sans export/import ni stockage persistant demandé. |
| CI / livraison | 🟠 Moyen | Pas de CI sur les PR ni sur `claude/**`, Node 20 (fin de vie), chaque push sur `main` part en production. |
| Documentation | 🟠 Moyen | Pas de README, docs mélangeant FR/EN, `DEVELOPMENT.md` sert aussi de journal des versions. |
| Processus | 🟠 Moyen | ~50 commits en 4 jours (32 le 19/10), versions `.01` à `.44` dans la même journée, montée de version manuelle dans 4 endroits. |

**Les 5 priorités :**
1. Faire tourner la CI sur toutes les branches et PR, et protéger `main` (P1).
2. Rendre les dates indépendantes du fuseau horaire (P1).
3. Ajouter export/import des plans et `navigator.storage.persist()` (P1).
4. Automatiser la montée de version (un seul endroit) (P2).
5. Rendre le code lisible : formatage automatique, puis découpage progressif de `planif-ui.js` (P2/P3).

## 2. Points forts (à conserver)

- **Architecture moteur / UI** : `planif-engine.js` est pur (pas de DOM ni de stockage), utilisable dans Node et le navigateur via `createEngine()`. C'est ce qui rend les tests possibles. À préserver absolument.
- **Règles séparées** (`planif-rules.js`) et **base de preuves** (`planif-studies.json`, `planif-evidence.js`) avec audit d'intégrité : rare et précieux pour une application d'entraînement.
- **Honnêteté scientifique** : les seuils d'organisation sont étiquetés comme heuristiques Planif, les sources sont tracées (DOI, PubMed).
- **Tests de non-régression par empreintes** + scripts d'audit (`scripts/audit-*.cjs`) qui reconstruisent l'ancien moteur depuis Git pour prouver que seuls les changements voulus apparaissent.
- **Protection des plans existants** : archivage avant migration, idempotence, semaines commencées non modifiées, erreurs d'écriture visibles.
- **Sécurité front** : CSP sans `unsafe-inline`/`unsafe-eval` pour les scripts, hash du bootstrap inline vérifié par test, SRI sur le SDK Firebase épinglé, `object-src 'none'`, `form-action 'none'`.
- **COROS** : PKCE S256 + `state`, pas de secret embarqué, aucun nouvel essai automatique d'écriture, anti-doublons, vérification de l'empreinte du schéma d'outil avant envoi.
- **Vérification post-déploiement** (`verify-live.cjs`) : compare les fichiers publics au commit.
- **Zéro dépendance runtime** : surface d'attaque supply-chain minimale.

### 3.4 Sécurité

| ID | Gravité | Constat | Recommandation |
| --- | --- | --- | --- |
| SEC-1 | P2 | 29 affectations `innerHTML` dans `planif-ui.js` à partir de gabarits. Les données externes (noms d'activités Strava, nom du compte) sont échappées dans `planif-strava.js`, et les titres de plans sont générés. Mais il existe **trois fonctions d'échappement différentes** (`esc`, `escape`, `escA`/`savedPlanEscape`) et rien n'empêche qu'une future donnée saisie ou importée (cf. ### Constats complémentaires (lot L3)

- **TZ-2 précisé** : le moteur est déjà indépendant du fuseau (252 plans de référence identiques sous 9 fuseaux une fois la sérialisation normalisée). Le risque réel était à la relecture : un plan sauvegardé à Paris puis ouvert ailleurs (Londres compris) décalait chaque séance d'un jour. Corrigé par l'enregistrement du fuseau (`dateZone`) et la conversion au chargement.
- **TZ-3 précisé** : l'application validait correctement la date COROS en jour local ; c'est le test qui utilisait le jour UTC. L'échec ne se produisait qu'à certaines heures (Auckland entre 0 h et 13 h locales).
- **AUD-1 (nouveau, P3)** : `npm run audit:planning` échoue aussi sur `main` (« plan envelope 0 block », champ `loadModel` ajouté en 2026.10.21.04). Le script historique n'a pas été mis à jour après la charge personnalisée ; à reprendre avec le lot L6. Il demande un clone Git complet (`git fetch --unshallow`).

### Constats complémentaires (lot L4)

- **SEC-1 élargi** : en plus des trois fonctions recensées, deux échappements manuels existaient dans l'interface (message de déplacement du calendrier, attributs de l'outil d'endurance). Tous passent désormais par `PlanifHtml.escapeHtml`, et un test interdit toute autre implémentation. Le titre du plan actif était inséré sans échappement ; c'est corrigé.
- **Import** : plutôt que d'échapper chacun des nombreux gabarits qui affichent le contenu d'un plan, l'import refuse tout `<` et toute clé de prototype. Planif n'en écrit jamais (vérifié sur les 252 plans de référence) ; combiné à la CSP sans script inline, un fichier importé ne peut pas injecter de balise.
