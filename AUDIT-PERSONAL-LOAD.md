# Personalized program load — 2026.10.21.04

The program now reports the same personalized points as the calculator. The shared functions live in `planif-engine.js`; the UI imports them. Work parts are charged separately at their prescribed speeds. Warm-up, cooldown, unspecified easy running and jog recoveries count at 0.20 point/minute. There is no additional density multiplier in the displayed points. Session ranges use the least/most costly options and the week sums the items actually placed on its dates. Active endurance and S1 within long runs are included.

This remains a Planif heuristic inspired by Daniels, not a validated physiological measurement: S1 = 240 min / 0.30, S2 = 60 min / 0.60, VMA = 6 min / 1.00. Specific pace coefficients interpolate on log race time; the speed curve interpolates between those points. At 105% VMA the factor is 1.20 and at 110% it is 1.50.

## Safety and unsupported inputs

Changing the point scale must not loosen training limits. Assembly retains the old safety accounting for candidate/format choice, heavy-week classification (historical work points / volume >= 0.18), the most costly quality, and recovery placement. Public load fields are converted after assembly. The original safety result is retained as `safetyLoad`. Minute caps, 35%/50% duration budgets, assimilation, dates and all workout structures are unchanged. A universal scaling of the 0.18 threshold would be inaccurate because the conversion ratio depends on intensity.

When predicted race paces contradict the fixed thresholds, personalized accounting falls back to the fixed speed anchors with a visible notice. For a race estimate outside 6–240 minutes, that pace uses speed-anchor interpolation rather than extrapolating its duration coefficient. Above 110% VMA (notably hill sprints at 115%), the higher historical coefficient is retained as a conservative, explicitly labelled exception. The calculator uses these same fallbacks. Optional strides with no prescribed speed cannot be assigned an invented intensity; the existing preparation/easy duration accounting is retained.

## Stored plans

No sessions are regenerated by the charge migration. Before the active plan is changed, an unmodified copy is archived; the existing archive history is retained. Only wholly future weeks without completed sessions are converted. Any week already started (including today), or containing a completed session, is left intact, including its original point scale. That avoids mixing two scales within one week. The UI identifies the retained weeks. Cached Strava validations are checked before asynchronous authentication is ready. Recovery mode, pending reference application and structure editing defer migration. The version marker makes it idempotent. Failed storage writes leave the active plan unchanged and show an error.

`tests/program-load.test.cjs` checks exact block/weekly sums, no density surcharge, shared coefficients, complete placed-calendar totals, idempotence, past/completed protection, cached validations, archive ordering and storage failure. The existing full suite retains its safety and structure assertions.
